## C2：四边形表 + 分页流式（当前）

三角形表改成每四边形一条投影记录（约 200 B/quad），tile 内再拆成两个三角形；
半透明三角形单独保存用于深度排序。像素输出保持不变。

| 000002 精确 | 原始 | 四边形表 | 分页流式 |
|---|---|---|---|

| 渲染 | 13.5 s | 6.6 s | 4.3 s |

## C5：紧凑属性 + 聚合并行化（当前）

### 聚合并行化

按输出 Y 行切块并行扫描，每块写入自己的 chosen state id；随后单线程按
y/z/x 顺序重写 palette 索引。palette 顺序和 packed 结果与单线程完全一致。

| 用例 | 之前 | 现在 |
|---|---|---|
| 000001 LOD 2 | 634 ms | **210 ms**（扫描 537 → 68 ms） |
| 000001 LOD 4 | 1,744 ms | **189 ms** |
| 000001 LOD 8 | 634 ms | **155 ms** |
| 000002 LOD 2 | ~1,844 ms | **419 ms** |
| 000002 LOD 8 | 1,204 ms | **197 ms** |

### 颜色 / UV 定点压缩

- UV 用 Q12 `i16`（实测 000001 的 4.74 亿个顶点全部可精确回读）
- AO 只有 4 档：0.55 / 0.7 / 0.85 / 1.0，用 2 bit 级数表示
- 四边形共享 color / normal / texture / shade，渲染表只存一份
- `Vertex` 44 → **36 B**，`Quad` 180 → **148 B**
- 投影四边形表 200 → **128 B**，半透明三角形 160 → **112 B**
- 重算颜色使用与旧路径相同的 f32 表达式，PNG SHA 不变

| 用例 | 优化前峰值 | 优化后峰值 | 墙钟 |
|---|---|---|---|
| 000001 精确 | 23,103 MB | **18,915 MB** | 36.6 s |
| 000002 精确 | 7,494 MB | **6,262 MB** | 30.4 s |

000001 精确图、000002 精确图、000001 auto（LOD 2）的 PNG SHA-256 均与优化前
完全一致。

注意：曾尝试在每页构建后 `shrink_to_fit`，000002 峰值只降 57 MB，却让建网格
时间从 24.8 s 涨到 31.1 s，因此没有保留。

## C6：容器 NBT 不再参与渲染（当前）

- `mesh` / `bench` / `render` 默认跳过 `TileEntities` 的 NBT，不分配其内容
- `inspect` / `validate` / `stats` 仍保留；需要跳过时加 `--ignore-block-entity-nbt`
- 如果 NBT 流在 `TileEntities` 中途结束，保留之前的方块数据，缺失的 block
  entity 当作空列表
- `test-No2/12345.litematic` 与 `all_ones_nbt_10GB.litematic` 相同：115 个木桶
  的书页共 10,000,526,997 字节，分成 9,538 个 gzip member；方块数据在第一个
  member 内
- 现在 12345 解析 6 ms、渲染 **0.32 s / 22 MB / 462 三角形**，不再报
  `TRUNCATED_INPUT`

## 观察

1. **000003 和 000004 是实心体**，LOD 后基本坍缩成一个盒子：LOD 4 是 73,728
   个三角形，LOD 8 是 18,432 个，正好是 4 倍关系。三到四秒完成，内存 85 MB。
   精确网格也只有 1,179,648 个 quad，所以这两份文件根本不需要 LOD。
2. **聚合性能已修复并并行化**：改成“全局状态 id + HashMap 计数”后，000002
   的 LOD 8 从 82 秒降到 2.0 秒，000001 的 LOD 8 从 6.1 秒降到 1.1 秒；
   按输出行并行后进一步降到 0.20 秒和 0.15 秒。
3. **000002 精确渲染可行但内存很高**：38.7 秒、19,558 MB、3980 万三角形。
   在 48 GB 机器上能跑，但 auto 预算选择了更稳的 LOD 2（25.2 秒、990 万三角形）。
4. **`--lod auto` 按预算选择**：000003 直接精确（7.5 秒）；000001 选 LOD 2
   （16.4 秒、9.6 GB）；000002 选精确（30.4 秒、6.3 GB）。
5. **000003/4 的 LOD 1 已经跑过**（精确 1.18M quad），不需要数亿 quad 的假设。
6. **全部已完成用例都在 10 分钟预算内**，最慢 38.7 秒（000002 精确）。
7. 大文件的精确渲染会触发 supervisor 默认内存上限，极端任务需要显式放宽
   `--memory`。
8. **LOD 不会把方块删掉，只会合并**：000001 在 LOD 4 下是 148,877 个单元，
   LOD 8 下是 19,683 个（27³），两次的 `blocksVisited` 与 `blocksRendered`
   完全相同，说明没有任何单元变成空气。损失的是分辨率（每个单元代表 64 或
   512 个原始方块）和状态多样性，而不是占用。
9. 因为聚合忽略空气，稀疏结构反而可能被"放大"成一个完整单元；如果希望
   稀疏处变薄，需要另加覆盖率阈值，而不是当前的多数规则。

## 待办

- 聚合可以按输出单元并行；当前是单线程扫描（000002 精确网格的主要成本是
  遍历 5065 万方块，不是聚合）。
- 视需要补测 000003/4 的 auto 结果（000004 未单独跑，预期与 000003 相同）。
- 若要进一步降低 `000001` 精确渲染的 23 GB，可把四边形表的颜色/UV 改成
  定点压缩；分页流式已经把全局表去掉，剩下的主要是网格本身和半透明排序表。
