# 极端投影渲染测试日志

环境：

- Windows 11，Ryzen 5 5500（6C/12T），48 GB 内存
- release 构建，客户端 jar `26.2-Fabric`
- 输出 1024x1024，超采样 2，`--threads 12`，`--force-limits`
- 峰值工作集（WS）由外部每 100 ms 采样，可能漏掉更短的峰值

命令模板：

```powershell
cargo run -p renderd-cli --release -- render "fixtures\private\<file>.litematic" `
  --output "renders\<name>-lod<L>.png" `
  --width 1024 --height 1024 --supersample 2 --threads 12 --lod <L> `
  --force-limits `
  --client-jar "D:\hmcl\.minecraft\versions\26.2-Fabric\26.2-Fabric.jar"
```

## 观察

1. **000003 和 000004 是实心体**，LOD 后基本坍缩成一个盒子：LOD 4 是 73,728
   个三角形，LOD 8 是 18,432 个，正好是 4 倍关系。三到四秒完成，内存 85 MB。
2. **000002 是聚合阶段的异常点**：同样单 region、无空气，LOD 8 花了 81 秒，
   而方块更多的 000003/4 只要 2.6 秒。聚合本身扫描的方块数一样（5065 万），
   LOD 8 每单元采样 512 次，状态又高度多样，当前实现用 `Vec` 线性查重，
   单元内接近 O(n²)。LOD 4 每单元 64 次采样，所以只用了 15 秒。
3. **000003/4 的 LOD 1 没有测**：按 000001 的比例推算会是数亿 quad 和几十 GB，
   没有现实意义；需要精确结果时应该换更大机器或继续提高 LOD。
4. **全部已完成用例都在 10 分钟预算内**，最慢 82 秒；LOD 4 是最稳妥的默认档。
5. 三个大文件的 LOD 4 峰值内存都远低于 supervisor 默认上限，但 LOD 1 会触发
   `MEMORY_LIMIT`，极端任务需要显式放宽 `--memory`。
6. 000002 的 LOD 8 虽然最慢，但内存最低（128 MB），说明慢在聚合算法而不是渲染。

## 待办

- 聚合计数改成按全局状态 id 的 `HashMap`，消除单元内线性查重的平方复杂度；
  预计 000002 LOD 8 从 81 秒降到个位数秒。
- 聚合可以按输出单元并行；当前是单线程扫描。
- 视需要补测 000003/4 的 LOD 2，确认曲线。
