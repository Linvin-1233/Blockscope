# 极端投影渲染测试日志

环境：

- Windows 11，Ryzen 5 5500（6C/12T），48 GB 内存
- release 构建，客户端 jar `26.2-Fabric`
- 输出 1024x1024，超采样 2，`--threads 12`，`--force-limits`
- 峰值工作集（WS）由外部每 100 ms 采样，可能漏掉更短的峰值

命令模板：

```powershell
cargo run -p renderd-cli --release -- render "fixtures\private\<file>.litematic" `
  --output "renders\<name>-lod<L>.png" `
  --width 1024 --height 1024 --supersample 2 --threads 12 --lod <L> `
  --force-limits `
  --client-jar "D:\hmcl\.minecraft\versions\26.2-Fabric\26.2-Fabric.jar"
```

## C2：四边形渲染表（当前）

三角形表改成每四边形一条投影记录（约 200 B/quad），tile 内再拆成两个三角形；
半透明三角形单独保存用于深度排序。像素输出保持不变。

| 墙钟 | 38.7 s | 32.4 s |
| 渲染 | 13.5 s | 6.6 s |
| PNG SHA-256 | `E861C6...` | `E861C6...`（一致） |

`000001` 精确估算约 29 GB（网格 13.5 GB + 四边形表 15.5 GB），仍需要至少
30 GB 空闲内存；当前 48 GB 机器只剩约 10~21 GB 可用，`--lod auto` 仍会选
LOD 2。显式 `--lod 1` 可以在空闲内存足够时精确渲染。

## 观察

1. **000003 和 000004 是实心体**，LOD 后基本坍缩成一个盒子：LOD 4 是 73,728
   个三角形，LOD 8 是 18,432 个，正好是 4 倍关系。三到四秒完成，内存 85 MB。
   精确网格也只有 1,179,648 个 quad，所以这两份文件根本不需要 LOD。
2. **聚合性能已修复**：改成"全局状态 id + HashMap 计数"后，000002 的 LOD 8
   从 82 秒降到 2.0 秒，000001 的 LOD 8 从 6.1 秒降到 1.1 秒。之前 81 秒
   是每单元线性查重的 O(n²)，状态越多样越慢。
3. **000002 精确渲染可行但内存很高**：38.7 秒、19,558 MB、3980 万三角形。
   在 48 GB 机器上能跑，但 auto 预算选择了更稳的 LOD 2（25.2 秒、990 万三角形）。
4. **`--lod auto` 按预算选择**：000003 直接精确（7.5 秒）；000001 选 LOD 2
   （12.9 秒、5.5 GB）；000002 选 LOD 2（25.2 秒）。
5. **000003/4 的 LOD 1 已经跑过**（精确 1.18M quad），不需要数亿 quad 的假设。
6. **全部已完成用例都在 10 分钟预算内**，最慢 38.7 秒（000002 精确）。
7. 大文件的精确渲染会触发 supervisor 默认内存上限，极端任务需要显式放宽
   `--memory`。
8. **LOD 不会把方块删掉，只会合并**：000001 在 LOD 4 下是 148,877 个单元，
   LOD 8 下是 19,683 个（27³），两次的 `blocksVisited` 与 `blocksRendered`
   完全相同，说明没有任何单元变成空气。损失的是分辨率（每个单元代表 64 或
   512 个原始方块）和状态多样性，而不是占用。
9. 因为聚合忽略空气，稀疏结构反而可能被"放大"成一个完整单元；如果希望
   稀疏处变薄，需要另加覆盖率阈值，而不是当前的多数规则。

## 待办

- C4：capacity 预算准入，超预算在分配前拒绝。
- 聚合可以按输出单元并行；当前是单线程扫描（000002 精确网格的主要成本是
  遍历 5065 万方块，不是聚合）。
- 视需要补测 000003/4 的 auto 结果（000004 未单独跑，预期与 000003 相同）。
- 若要让 000001 在 48 GB 机器上精确渲染，还需要再降约 4~8 GB：可考虑把
  四边形表的颜色/UV 改为定点压缩，或分页流式光栅化。
